# 实习生助手

一台没有独显的笔记本上，让本地小模型先把代码活干一遍：给它一个写错的函数和一段失败的测试，它改对；改不动的自动升级到网页上的大模型兜底。配套一份改过的 llama.cpp，让长上下文和 MoE 在纯 CPU 上别掉得那么难看。

> **状态：v1.0。**
>
> 流水线能跑完整闭环（读题 → 拼 prompt → 本地模型 → 塞回模块 → 跑测试 → 判分 → 升级 → 复核），llama.cpp 侧有两项改动拿到了单向收益、一项全通、两项验收失败已关闭、一项未实现。
>
> 下面的数字全部是这一台机器上的内部观测。**能复现的我标了「可复现」，不能复现的我标了「内部观测」并且不给结论强度**——题池和权重都不发布，别人拿不到同一套题和同一个模型，所以流程类的数字只能当参考，不能当成绩。

## 这是什么

我在自己那台机器上写代码，想让一个本地小模型先把活干一遍——改函数、补代码、修报错——干不动的再交给网页上那个大的。这样重复的活儿不用我盯着，也不花 API 钱。

它只做一件事：**给定一个函数和一段失败的测试，把函数改对**。不做对话、不做代码补全、不做代码解释。这不是谦虚，是能力边界，「已知限制」会讲为什么。

## 我为什么做这个

机器是 Ultra 7 155H，22 线程（6 性能核、8 能效核、2 低功耗核），32 GB LPDDR5x，没有独显。

第一版 README 在这里写的是「瓶颈是内存带宽，decode 阶段每 token 只能拿到约 31 GB/s」。**这个判断后来被自己的实测推翻了，记录在这里而不是悄悄改掉**：

- 单个大算子（LM head，615 MB 权重）跑出 **62~66 GB/s**，14 线程逐线程只差 0.4%——硬件能吃到的带宽比 31 高得多；
- 换成 MoE 模型全程只有 ~49 GB/s，稠密 Q4_K_M 全程只有 **40 GB/s**，而这两者的每 token 字节数差不了多少；
- 把 head 从 Q8_0 降级到 Q4_0，字节省了 47%，速度只涨 6%（16 线程），因为 Q4_0 每 32 个元素要多做一次 `shuffle_epi8` 查表解包。

⇒ 真实的瓶颈是**每元素的解包指令成本**，不是带宽。这一条改变了整套调优的方向：减字节不再等于提速，profiler 该看的是「每个 op 花了多少指令、负载分得多不均」。

设计上的两条结论没变：本地只放 2B 级模型（长活外包），以及长上下文会让 KV 读取反超权重读取——后者是 `-fa auto` 想解决的问题。

还有一条私人理由：不想为每次调用付钱，也不想把自己的代码贴给不认识的 API。所以兜底走网页版（免费），代价是要开一个浏览器、速度取决于对方页面。

## 它由哪几块组成

### 改过的 llama.cpp（`patches/llama-cpp-cpu-tuning.patch`）

基于上游 `5096f2a`（MIT），**16 个文件，+1239 / −130 行**。用 `scripts/setup_llama.sh` 一条命令能 clone → 退基线 → 打 patch → 编译。

| 改动 | 状态 | 收益 |
|---|---|---|
| **MUL_MAT_ID 抢块**（`repack.cpp`） | **已实现，4/4 轮单向** | decode **+5.7%**、prefill **+18.3%** |
| **op 级 profiler**（`ggml-cpu.c`，`GGML_OPPROF=1`） | 已实现，实测零开销 | 换模型十分钟定位瓶颈 |
| `-fa auto` 按 KV 长度动态切注意力路径 | **已实现，验收全通** | 2k +17% / 4k +45% / 8k +90% |
| KV 头分组重排 | 部分通过（8 条里 5 条） | 验收没过，**数字不对外说** |
| 量化 V cache 专用算子 | 验收失败，**默认关闭** | 代码留着但不参与计算 |
| prompt ledger（前缀复用记账） | 未实现 | — |

前两项是这一版新加的，也是唯一值得单独讲的：

**抢块**。MoE 的 `MUL_MAT_ID` 原本按专家静态切分——每个线程分到「某个专家的一段行」，专家之间大小不一时，快的线程干完就闲着等最慢的。改成从线程池计数器上领块（块对齐 `NB_COLS=8`，否则 gemv 会静默丢组）后，线程可以跨专家流动：

```
整图 max/mean 浪费   11.8% → 4.8%
MUL_MAT_ID 浪费      3761 → 666 μs
线程数最优点         14 → 18（22 线程从 −17% 变成只 −7%）
```

粒度 2 / 4 / 8 全在噪声内 ⇒ 收益来自**跨专家领活**，不是切得细。

⚠️ 这条改动有个必须知道的实现约束：**开关必须是编译期 `#define`**。我一开始把它做成运行期 `if`，哪怕 else 分支是空的、里面代码一字未改，`gemv<>` 这个巨型模板也会掉 **26%**（19.26 → 14.32 tok/s）。MSVC 见它落在分支里就不再生成同样的代码。策略开关挂 env / 运行期判断，在这条路径上等于自毁。

**profiler**。`GGML_OPPROF=1` 打一份按 op 聚合的表：每个节点的耗时、max/mean（负载均衡）、每逻辑 CPU 的相对成本。实测 19.29 vs 19.26 tok/s，零开销。它就是上面那张「浪费 11.8%」的来源，也是我这个项目里唯一沉淀成工具的东西。

### harness

读题、拼 prompt、调本地模型、收回复、把改完的函数塞回模块、跑测试、判分、出报告。模型只输出文本，不碰文件系统，所有 I/O 由 harness 执行。

### 升级链路

判分之后决定要不要升级，三段命中任一就升级：

- `fail`：测试仍然失败；
- `collateral`：测试绿了，但改动行碰到了目标函数以外的行——**这条最重要**。小模型很容易为了让测试绿顺手改掉邻居函数，账面通过、实际是灾难；
- `rewrote`：测试绿了，但整个函数被重写而非定点改动。

### 观察值路由（`--observe auto`）

prompt 里要不要给模型「第 N 条断言失败，实际得到 X，期望 Y」这一句，**不该由开关决定**。实测：

- 模块里**有多个函数**时，加了观察值 **17→20/27**：这类题的失败形态是「看得到代码，看不出哪行错」，模型常常把错误代码原样抄回（`footprint=0`）；观察值提供的是**必须跑一遍才知道**的信息，静态推不出来。
- 模块里**只有一个函数**时，加了反而 **17→15/21**：bug 静态可见，观察值信息量趋近零，副作用却是把注意力锚死在**那一条**断言上——有个测试里，模型为了迎合 `k=1` 那条断言，把原本正确的 `if k == 0` 守卫删了，结果 k=0 时崩。

判据是 `n_top_functions(module) > 1`（AST 数顶层 `FunctionDef`），不看题目自带的标签——题池里有 6 道标着 `solo` 的题其实带 `_private` helper，实测行为属 mixed 档。真实仓库没有这种标签，只能看代码本身。

合计 **38 → 41/54**。

诚实说统计口径：McNemar b=3 / c=0，**双尾 p = 0.25，不显著**。能主张的是方向单向、c=0、机制逐题可复现、两次独立运行一致；不能主张「统计证明更好」。

## 跑起来

### 需要什么

Windows + Visual Studio 2022（MSVC）、CMake 3.28+、Ninja、Python 3.11+。Linux / macOS 大概能编（MSVC 那边几个坑换 GCC 反而没有），但我没测过。

模型要自己下。**仓库不含权重**。

### 编译 + 打 patch

```bash
bash scripts/setup_llama.sh
```

也可以用 `DEST=` 指定 clone 位置，`SKIP_BUILD=1` 只打 patch。核心是这两句，想手动做就照这个来：

```bash
git clone https://github.com/ggml-org/llama.cpp && cd llama.cpp
git checkout 5096f2a42468daff7ff38d97b48bd17432196e98
git apply ../patches/llama-cpp-cpu-tuning.patch
```

`GGML_NATIVE=ON` 是故意的，别关——让编译器按你这台机器的 CPU 生成指令，关掉能跑但会慢一截，然后你会以为是 patch 没用。`GGML_AVX_VNNI` 保持默认关。

### 起服务

```bash
GGUF=/path/to/model.gguf bash serve_mcp2b.sh
```

默认 `-c 4096 -t 18 -fa on`。服务要一直挂着，**别用 `&` / `nohup` 起**——进程被回收时子进程跟着走，这个坑踩过不止一次。

### 跑

```bash
python harness.py --base-url http://127.0.0.1:8299 --problems 你的题.json --id <题号>
python harness.py --base-url http://127.0.0.1:8299 --problems 你的题.json --all --pause 3 --tag 第一次
```

不传 `--problems` 会找 `repair_eval/problems_hard.json`，那个文件**不在发布范围内**，所以自己跑一定要传。

题目格式：顶层 `{"problems": [...]}`，每道题给一个模块的完整源码、目标函数名、一组失败测试、一组不能回归的测试。

判分口径只有一句，必须写清楚，否则「通过率七成」在别人眼里就是「我觉得它行」：

> 通过 = 全部失败测试变绿，**且**改动到的行集合不与目标函数外的行相交。

### 兜底链路

`--cloud` 需要你自己准备一个已登录的浏览器和 CDP 端口。这部分绑账号，我没法把配置发出来，仓库里只有站点选择表（DeepSeek / Kimi），路径和选择器都得自己对着当前页面改。不想配也行：本地跑，失败的题记一笔，人工处理。

## 怎么调

**契约**（`--contract`）决定 prompt 里给模型什么，是最重要的一项：

- `module`：给整个模块，自己定位改哪个函数。最接近真实场景。
- `func`：只给目标函数，最省上下文，前提是你已经知道该改哪个。
- `auto`：从失败测试的 AST 里推出目标函数——取「测试里被调用到的名字 ∩ 模块里定义的函数 − 测试自己定义的函数」。真仓库没有标准答案，所以推断出来的名字直接当目标用，不跟任何 gold 比对。

**换模型必须重测契约**，别默认能带过去。同一个契约，两个模型的反应可以完全相反：我的 2B 在 `module` 下只有 26/54、`auto` 下 39/54；Qwen2.5-Coder-3B 反过来，`module` 36/54、`func` 只有 24/54。

**线程数**：默认 18。扫的时候两个坑——顺序从 12 扫到 22 会被「越跑越快」的漂移骗到 15%（升频 / 页热身），会把最后测的那个伪装成最优，必须正反交替；`t=14` 是最不稳的点（四轮里有一次掉 8%），大概率因为踩到 SMT 兄弟同核。另外**别想「避开慢核」**：profiler 显示 8 个逻辑核位稳定慢 8~10%，但只用 12 个快核（t=12）是最差配置，比 t=18 低 13%——慢核照样贡献带宽，少线程的损失大于核间差异。

**温度**固定 0。但它**不等于逐位可复现**：同一份 prompt 跑两次，54 题里会有 1 道翻面。所以单道题的输赢别当结论。

## 已知限制

这套东西只覆盖「拿到报错 → 改那个函数」这一段。「改哪个函数」是 harness 代劳的：`auto` 契约从 AST 推出来；模块源码是 harness 贴进去的；测试是 harness 跑的；判分也是 harness 做的。

真实派活还包括：从现象判断该看哪个文件、读相关代码、自己跑测试看修好没、改错之后自己重试。这些它一件都不做。

所以「首写通过率」的准确含义是：**在已经知道改哪个函数、模块代码已经递到手里、由外部判分的前提下，它写对的概率**。不是「派活能完成」的概率。

单独测过 `diag`（给一个报错让它指出哪一行）：处方大体对（52%），精确行号只有 17%。**会改不会指**。

本地通过率约七成。这不是「还没训好」——从 v4 一路训到 v7，分数没提升还略降，回退到 v4 定版。这条路走完了。

模型权重没发。原因不是体积（1.56 GB 放得下），是**权重离开训练时的 prompt 形态就没用**：它学的是「给单个函数 + 一段报错，我修」，换个输出形态掉三十个点。别人拿到 gguf 也复现不了我的数，反而会以为是我在吹。

能直接用的是一个公开模型：Qwen2.5-Coder-3B-Instruct（Q4）。我那批题上首写 36/54，单题慢一倍多——但要用它自己的最优契约（`module`）。想要更强就上 30B 级 MoE，比如 Qwen3-30B-A3B 的 Q3_K_M：这台机器装得下、跑得动，但每题从秒级变几十秒，适合夜里批处理。

## 不要这么干

**不要用上游最新的 llama.cpp 去打这个 patch。** 它对着 `5096f2a` 做的，上游每周几十个提交，ggml 那块重构频繁，打不上时报错会指到一个跟你改动无关的地方，很难看出真因。先 `git checkout 5096f2a`。

**不要把策略开关做成运行期 `if`。** 见上面抢块那节：包进运行期分支、代码一字不改，`gemv<>` 掉 26%。要开关就用 `#define`。

**不要改 prompt 模板里的段落顺序。** 模型的输出格式跟结构绑着，顺序一换它就开始解释思路，解析直接失败。要改就整段替掉，别调位置。

**不要给小模型开思考模式。** 实测一次性可用率掉 7.4 个百分点，炸邻居率 7% → 33%，墙钟慢十七倍，定位命中率一点没变。它的 CoT 是装饰性的。

**不要只靠测试绿判断改对了。** 小模型会为了让测试通过去改无关函数，一行测试结果看不出这个，必须比对改动行。

**不要拿这套流程的分数跟别人比。** 题池是我自己造的，没有外部效度。要比，用你自己的测试集跑两边。

### 内部观测（不可复现，别当成绩）

| 项 | 数 |
|---|---|
| 54 题池首写通过（v4 2B，`func` + observe 路由） | **41/54**，4.6 s/题 |
| 同上，端到端墙钟（含升级） | 683 s → 638 s（−6.6%，45/54 更快） |

## 同类项目

如果你的问题是「内存装不下模型」，去看他们，别看我这个。

**smolmaxxing**（`hyperionaidev/smolmaxxing`，MIT）：llama.cpp patch 组，目标是在 1 GB 可用内存的电视盒子上跑 8B/16B MoE。手段是定制内核、LM head 剪枝、专家从闪存分页。它把 165 个实验记录全公开了，失败的也在里面——那份记录比结论有用。

**Edge0**（`Edge0-AI/Edge0`，引擎 Apache-2.0，模型另一套许可）：自成一套推理框架 + 模型家族，训练阶段就学一个路由预测器，推理时按预测提前把专家权重从 SSD 预读进来。

一句话关系：**它们解决「装不下」，我解决「装得下但上下文一长就慢、MoE 专家之间负载不匀」**。我有 32 GB 内存，2B 到 6B 都装得下，分页和流式加载对我没价值。

有个对照值得记：它们都把不确定性**挪到前面**（构建期剪枝 / 训练期学路由），我是**运行时判定**。方向相反但不矛盾——对话会有多长，构建期确实不知道；而一个 token 会激活哪些专家，可以从训练数据里提前学。**不确定性能在哪一层消掉，就该在哪一层消掉。**

它们都指向我还没碰的方向：MoE。同样每 token 字节数，MoE 能把参数量抬一个档。下一步是换 30B-A3B 这类模型，而不是继续在小 dense 模型上抠内核。
